# Typed commands

Manual-only entries request deliberate selection: `/<name>` in Claude Code, `$<name>` in Codex. Host policy suppresses implicit selection; it does not prevent filesystem reads or required composition. Each entry below explains the practical reason to select that workflow explicitly; the catalog records the preference, not a historical rationale.

Typing a command selects a skill and a mode. It never grants extra authority: a command that drafts still only drafts until you ask it to file, push or merge.

## How typing works on each host

| Host | Syntax | Example |
| --- | --- | --- |
| Claude Code | A leading slash, then your request on the same line. | `/grill-me split the billing service into two deployables` |
| Codex | A dollar sign, then your request. | `$grill-me split the billing service into two deployables` |
| T3 Code | The syntax of the host running that thread. | `/grill-me ...` in a Claude thread, `$grill-me ...` in a Codex thread. Not separately tested. |

Type the command at the start of your message. The Claude Code evals typed a leading `/<name>`; most Codex evals typed a leading `$<name>`.

Saying the name in a sentence is not the same. In the PR #5 Codex evals, prompts that only named a typed-only skill in words did not reliably load it, so the remaining cases switched to `$<name>`. In the PR #7 Codex evals, a plain "Full send this" loaded neither `full-send` nor `full-stop`.

This page documents recorded native invocation for the manual entries. Explicit selection of other entries depends on host behavior; these records do not establish every such command.

## What typed only means, and what it does not

The catalog marks these skills `invocation: user`. Each host enforces that differently:

| Host | Enforcement | Effect |
| --- | --- | --- |
| Claude Code | `skillOverrides` set to `user-invocable-only`, written by the installer's `--host claude` adapter. | The skill stays listed and typeable, but is hidden from the model's own skill list. |
| Codex | `agents/openai.yaml` with `policy.allow_implicit_invocation: false`, generated into the skill folder. | Codex does not select the skill implicitly; `$<name>` still selects it. |

Three things typed only does not do:

- **It does not stop other skills from reading it.** A skill that requires a typed-only skill still reads it by name. `implement-spec` reads `implement`, `full-stop` reads `full-send`, and `agent-orchestrator` reads `to-spec`, `to-tickets`, `grill-with-docs`, `implement-spec` and `retro`.
- **It is not a lock on the file.** A model that already knows the path can read the `SKILL.md` from disk. The evals saw this once on each host: `to-questionnaire` on Claude Code, which a fresh repeat did not reproduce, and `teach` on Codex, fixed by narrowing its description. See [known issues](known-issues.md#manual-only-is-not-a-file-access-boundary).
- **It grants no authority.** `/pr` drafts by default and files when the same request or existing task authority permits it. `/full-stop` never merges. An explicit request to merge supplies merge authority; the `full-send` method owns the guarded procedure. Loading a command supplies no authority beyond the request.

The catalog records which skills are typed-only, not why. The reason given in each section below follows from what that skill does.

Seven entries are thin: they open another skill in one mode and add no method of their own. They are `/grill-me`, `/bro`, `/wait-what`, `/pr`, `/full-stop`, `/council` and `/interrogate`. If the skill a thin entry opens is not installed, the entry says so and stops instead of improvising; the Claude Code evals recorded this for `/bro`, `/pr` and `/full-stop`.

## Shaping and planning

### `/grill-with-docs`

- **Typing it:** starts an interview about your plan, with the glossary and decision records updated as answers land.
- **Opens:** the `grilling` interview with the `domain-modeling` discipline active.
- **Needs:** `docs/agents/domain.md` from `/setup-agent-skills`. Without it, the skill says so and offers a plain interview with no doc writes.
- **Changes:** writes each settled term to the configured glossary, and an ADR only when a decision is hard to reverse, surprising without context, and a real trade-off, and you accept it. Commits, code and tracker writes need their own request.
- **Close:** the settled decisions, anything deferred, every glossary and ADR change with its path, and `/to-spec` as the next step when the result is a build. It can run one optional "builder check", a fresh reader of the close, charged to the run's budget.
- **Why typed only:** it writes project documents. A plain interview, which writes nothing, is the auto default.
- **Example:** `/grill-with-docs we want partial refunds on orders`

### `/grill-me`

- **Typing it:** starts the same interview in no-doc mode.
- **Opens:** the `grilling` skill, no-doc mode.
- **Changes:** nothing. The result lives in the conversation. If you ask it to record terms, it names `/grill-with-docs` and switches only on your word.
- **How the interview runs:** numbered rounds; each question has a recommended answer, worded so "yes" accepts it. Facts are looked up, not asked. Settled choices are listed, not re-asked. It stops when the remaining answers would not change the plan, and waits for you to confirm the close.
- **Why typed only:** "grill me" turns up in notes and logs. Asking in words ("grill me on this plan") already reaches the auto `grilling` skill, so the typed form is a shortcut, not a new method.
- **Example:** `/grill-me split the billing service into two deployables`

### `/to-spec`

- **Typing it:** writes the agreed plan as an engineering spec. It does not interview you.
- **Opens:** a full skill; it uses `domain-modeling` for the glossary's terms.
- **Output:** numbered user stories, each with **Acceptance** and a **Proof** (the real surface to drive and the result to see there), the proposed testing seams, open questions with who decides them, and a Sources list with each file's SHA-256.
- **Changes:** files the spec where `docs/agents/issue-tracker.md` says, when filing is within your request. Without tracker setup, or with a draft-only request, it returns the draft in the conversation.
- **Why typed only:** you decide when the plan is agreed, and filing writes to a tracker.
- **Example:** `/to-spec write up what we agreed for saved searches`

### `/to-tickets`

- **Typing it:** splits an approved spec into vertical-slice tickets and asks you to review the breakdown.
- **Opens:** a full skill.
- **Output:** a numbered list, each ticket with its title, **Blocked by**, what it delivers, its **Proof** and the stories it covers. You approve, merge or split, then it files.
- **Changes:** one `NN-slug.md` file per ticket in the local ticket folder, or one issue per ticket on a remote tracker, in dependency order. For local tickets, when `work-decomposition` is installed, it runs that skill's importer and fixes every `FAIL` line before reporting.
- **Rules it keeps:** wide refactors become expand, migrate in batches, then contract. Ticket numbers and approved wording stay stable once filed.
- **Why typed only:** it files tickets, and the breakdown needs your approval.
- **Example:** `/to-tickets docs/specs/saved-searches.md`

### `/triage`

- **Typing it:** shows what needs triage, or triages a named issue or external PR.
- **Opens:** a full skill; it uses `grilling` for real gaps and `domain-modeling` for terms.
- **Roles it applies:** one category (`bug` or `enhancement`) and one state (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`), mapped to your labels by `docs/agents/triage-labels.md`.
- **Changes:** label changes you direct; comments, briefs, closes and out-of-scope records only when you ask or approve the draft. Issue and PR text is treated as untrusted data, and PR code runs only in isolation.
- **Why typed only:** it changes tracker state that other people see.
- **Example:** `/triage what needs attention?` or `/triage move #42 to ready-for-agent`

### `/wayfinder`

- **Typing it:** charts a goal too big and unclear for one session as a map of decision tickets, or works the next ticket on an existing map.
- **Opens:** a full skill; it uses `research`, `prototype`, `grilling` and `domain-modeling` for its ticket types.
- **How it runs:** charting is one session and resolves nothing. After that, each session claims and resolves one ticket. Research tickets may be batched. Decisions, not deliverables, are the output; a build hands off to `/to-spec` and `/to-tickets`.
- **Changes:** local map files by default; a remote tracker only when you ask to publish the map. No branches, pushes or PRs.
- **Why typed only:** it is a multi-session planning mode that creates a map and tickets.
- **Example:** `/wayfinder we should move billing off the monolith`

### `/to-questionnaire`

- **Typing it:** drafts a questionnaire for one person who knows what you do not.
- **Opens:** a full skill.
- **How it runs:** it asks only for a missing recipient, purpose or need, in one message, never about the subject itself. Questions target the gap between what the recipient knows and what you need.
- **Changes:** writes `to-questionnaire-<slug>.md` in the current folder, or the path you name. It never sends, posts or publishes.
- **Why typed only:** it creates a document meant for another person. One Claude Code eval saw a plain survey request read this skill's file from disk; a fresh repeat did not.
- **Example:** `/to-questionnaire ask the finance lead how refunds are reconciled today`

### `/setup-agent-skills`

- **Typing it:** creates or updates the project contract the shaping skills read.
- **Opens:** a full skill.
- **Changes:** one `## Agent skills` block in your project instruction file, plus `docs/agents/issue-tracker.md`, `docs/agents/domain.md` and, when `triage` is installed, `docs/agents/triage-labels.md`. It keeps existing paths and labels, creates glossary and ADR files lazily, and repeats without new changes.
- **Not included:** creating remote labels or issues, global settings, hooks or host invocation policy.
- **Why typed only:** it edits your project's instruction files.
- **Example:** `/setup-agent-skills use GitHub issues and a single glossary`

## Understanding and wording

### `/sharpen`

- **Typing it:** rewrites your prompt into a deeper version of the same task, without doing the task.
- **Opens:** a full skill. Its body is the upstream pstack text, unchanged.
- **Output:** what a top professional would add, the rawest starting material, the methods and tools, and what outside the conversation would show the result is right; then the rewritten prompt, with choices that are yours left open.
- **Why typed only:** if it triggered on its own, ordinary requests would come back as rewritten prompts instead of results.
- **Example:** `/sharpen write a migration plan for the orders table`

### `/bro`

- **Typing it:** repairs the agent's last answer in plain words.
- **Opens:** the `clear-communication` skill, "Repair your own last message" mode.
- **Keeps:** every fact, number, caveat and limit of the original answer. It starts no new task.
- **Why typed only:** "bro" is an everyday word, and quoted uses must select nothing.
- **Example:** `/bro`

### `/wait-what`

- **Typing it:** explains the one point in the last answer that lost you, in your project's terms.
- **Opens:** the `clear-communication` skill, the same repair mode with added context.
- **Keeps:** stated evidence limits, such as "static only" or "not run in the UI". It creates no course or document.
- **Why typed only:** same as `/bro`.
- **Example:** `/wait-what what does settlement mean here?`

### `/teach`

- **Typing it:** explains a concept or subsystem in layers: a plain definition first, then mechanism, rationale, examples and edge cases, as deep as you asked.
- **Opens:** a full skill; it requires `clear-communication`, `how` and `why`.
- **Changes:** nothing by default. Only when you ask to save a course does it write a learning workspace (mission, resources, lessons, progress) at your chosen path.
- **Quizzes:** only when you ask for them.
- **Why typed only:** ordinary explanations should stay ordinary. `how` and `why`, which are auto, answer most questions without it.
- **Example:** `/teach how does the export queue retry failed jobs?`

## Design, build and review

### `/improve-codebase-architecture`

- **Typing it:** surveys the codebase, starting from the files that change most, and proposes deepening refactors.
- **Opens:** a full skill; it requires `codebase-design` for its vocabulary.
- **Output:** a static, offline HTML report written to your temporary folder, never the repository, with one card per candidate: files and lines, problem, solution, wins, before and after, evidence and strength. Then it asks which one to explore.
- **Changes:** no product code before you pick a candidate and authorize work. Diagrams load Mermaid from a CDN only if you accept that.
- **Why typed only:** a whole-codebase survey is expensive, and its output is a report you review.
- **Example:** `/improve-codebase-architecture focus on the billing package`

### `/implement`

- **Typing it:** builds one approved ticket, spec slice or agreed change, proves it, and reviews it.
- **Opens:** a full skill; it requires `tdd` and `change-review`.
- **How it runs:** reads the acceptance and Proof; rules on contradictions with the spec as the authority, and records each ruling; builds test-first where a meaningful seam exists; runs the relevant suite; cleans its own diff; reviews it against the ticket.
- **Changes:** code in the slice; a commit only when committing is within your request. Push, PR and tracker updates need their own request.
- **Report:** COMPLETE, PARTIAL or BLOCKED first, then the Proof's command and observed result.
- **Why typed only:** it changes code. Coordinators reach it through `/implement-spec`, which tells each worker to read it.
- **Example:** `/implement ticket 03`

### `/implement-spec`

- **Typing it:** runs a whole approved ticket graph to one integrated, verified branch.
- **Opens:** a full skill; it requires `work-decomposition`, `agent-briefing`, `decision-log`, `result-verification` and `implement`.
- **How it runs:** imports the tickets exactly, sets a finite budget before the first start, keeps a run record on disk (`PLAN.md`, `LOG.md`, `DECISIONS.md`), briefs one worker per ready ticket, accepts each on a rerun of its Proof, reviews within three fix rounds by default, merges into the integration branch and runs every acceptance check there.
- **Limits:** one coordinator owns every start; at most eight subagents run at once, or fewer if your host or you set fewer. When the host cannot dispatch workers or isolate checkouts, it stops at a source-bound preflight and reports execution as blocked.
- **Why typed only:** it starts many agents and spends a model budget.
- **Example:** `/implement-spec docs/specs/saved-searches.md`

### `/council`

- **Typing it:** asks for a panel of distinct providers on a question.
- **Opens:** a code review and fix loop goes to `sol-loop` in panel mode; a design or other non-code question goes to `agent-debate` in panel mode. A read-only request wins: code then opens `change-review` as a report-only panel.
- **Keeps:** the providers you named. A missing one is reported as unavailable, never replaced.
- **Why typed only:** "council" is an ordinary word, and every panel seat costs a model start.
- **Example:** `/council review this branch with Claude and Codex, report only`

### `/interrogate`

- **Typing it:** runs a report-only adversarial review that tries to break the change with targeted probes.
- **Opens:** the `change-review` skill in panel probe mode, with no fix loop.
- **Evidence rules:** a runtime claim needs an executed probe; a static claim keeps its static proof; an unrun runtime claim stays an open hypothesis under its finding ID. Every probe attempt, including failures and repeats, counts against the declared allowance.
- **Why typed only:** probes run commands against your code, and it is an explicit mode.
- **Example:** `/interrogate try to break the new export path`

### `/maintain-verification-skill`

- **Typing it:** audits an existing project driver (a skill that launches and drives the real app) against source and real behavior.
- **Opens:** a full skill. It does not need `create-verification-skill`.
- **Output:** **clean**, **changed** or **blocked**, with each finding classed as recipe drift, a harness gap, an environment block or a product regression.
- **Changes:** only the driver's own files, and only when edits are authorized. Product regressions are reported, never repaired here.
- **Why typed only:** a full audit drives the real app across every declared feature.
- **Example:** `/maintain-verification-skill verify-notes-web`

## Shipping

### `/pr`

- **Typing it:** writes the PR title and body for the current change as a local draft.
- **Opens:** the `file-pr` skill, body-only mode.
- **Changes:** nothing remote. Ask in the same message to file or update ("`/pr` and open it as a draft"), or preserve existing filing authority; it then uses file-pr's file mode.
- **Body shape:** the repository's template and recent merged PRs decide it. Without one: Why, What changed, Scope, Evidence, Risk, Tradeoffs.
- **Why typed only:** "pr" appears in almost every coding conversation.
- **Example:** `/pr`

### `/full-send`

- **Typing it:** hands the agent the whole delivery, to a merged PR.
- **Opens:** a full skill; it requires `file-pr`, `babysit-pr`, `sol-loop` and `result-verification`.
- **It grants:** merging once the gate passes, a force-push of this task's own branch with a captured lease after a rebase, and the tests its Proof needs without asking first. It does not grant production changes, data deletion, closing PRs or force-pushing other branches.
- **Merge gate:** Proof covers the diff; required checks, bots and approvals from repository policy are present; every review thread, however old, is addressed; no human review requests changes; the branch is current and mergeable; and the work stayed within three review rounds by default. It merges with a head guard, then reads the merge back.
- **Why typed only:** it selects the full delivery scope; an explicit merge request can also authorize that scope.
- **Example:** `/full-send fix the off-by-one in the pager and get it merged`

### `/full-stop`

- **Typing it:** does everything `/full-send` does except merge, and leaves the PR open and ready.
- **Opens:** the `full-send` skill, prepare-only mode.
- **Keeps:** no-merge in every helper and child. It cancels auto-merge or merge-queue entries the run owns, and reads back that none remain.
- **Ends with:** ready to merge, waiting for required approval, or blocked, with the PR link and final head.
- **Why typed only:** "full stop" is ordinary punctuation and emphasis.
- **Example:** `/full-stop get this ready for review`

## Continuity

### `/retro`

- **Typing it:** compares what this session did with what you asked for, and finds the smallest supported improvement.
- **Opens:** a full skill; it requires `writing-for-agents`.
- **Evidence rules:** when you name the allowed project and history sources, it reads exactly those paths, without directory listings or broad status/search; Git history is a separate source used only when named. Installed method references remain method inputs. Missing history stays unknown.
- **Prefers:** a check, type, lint or wired test over a new written rule; a recurring mistake goes to the `correct` skill.
- **Changes:** edits only within your request; otherwise a proposal. No public issues or global settings.
- **Why typed only:** a retrospective runs only on request; finishing work does not start one.
- **Example:** `/retro why did the last run reread the spec three times?`

### `/handoff`

- **Typing it:** writes a continuation note so a fresh session can pick up exactly where this one stands.
- **Opens:** a full skill.
- **Changes:** one note in the operating system's temporary folder, outside the workspace, with restricted permissions. It links the run record, spec, branch and PR rather than copying them, and lists suggested skills.
- **Keeps:** the spent budget, active workers, open choices and the next ready action. Secrets are redacted.
- **Why typed only:** you decide when a session ends. Temporary folders can be cleared; a durable run record belongs to `decision-log`.
- **Example:** `/handoff next session should finish the import tests`

### `/ketchup`

- **Typing it:** catches you up on everything since your last message: what changed, the real state of PRs, CI and agents, and every choice still waiting on you.
- **Opens:** a full skill; it requires `clear-communication`.
- **Changes:** nothing. It does not rerun CI, start watchers, post or merge.
- **Wider window:** ask for a period ("`/ketchup` for last week") and it resolves concrete dates and checks live state before calling anything shipped.
- **Why typed only:** the name is a pun on "catch up"; it runs only on request.
- **Example:** `/ketchup`
