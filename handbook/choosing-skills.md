# Choosing a skill

Find what you want to do, then use the skill in that row. Typed-only skills appear as `/<name>`: type them, or `$<name>` in Codex. For the others, say what you want in plain words; the phrases shown are examples, not required wording.

Each generated row includes an example prompt and a neighboring method to compare. The catalog owns membership and invocation mode; `intent-guide.json` supplies the human explanation and the README's categories. Every skill belongs to exactly one group. Missing or duplicate guidance is an error for any new skill.

## Pairs people mix up

### Interviews: `grilling`, `/grill-me`, `/grill-with-docs`

All three run the same interview: rounds of numbered questions, each with a recommended answer. `grilling` is the auto skill and writes nothing. `/grill-me` is the typed shortcut to exactly that. `/grill-with-docs` adds the glossary and ADR writes, and uses configured domain paths. Without those paths, it offers a plain interview with no document writes.

### Reviews: `change-review`, `sol-loop`, `/council`, `/interrogate`

`change-review` is the report-only primitive the others build on. `sol-loop` adds fixing, three rounds by default. `/council` makes it a panel of named providers. `/interrogate` makes it adversarial with executed probes, still report only. None of them replaces Claude Code's `/code-review` or `/review`.

### Explaining: `how`, `why`, `/teach`, `research`

`how` traces current execution from source. `why` reconstructs intent from history and labels each claim as direct, supported, inferred, speculative or unknown. `/teach` composes both into a layered lesson. `research` answers questions whose answer lives in outside primary sources.

### Building: `/implement`, `/implement-spec`, `tdd`

`/implement` builds one slice. `/implement-spec` coordinates many `/implement` workers over an approved graph. `tdd` is the test-first loop either of them uses at a meaningful seam; it also stands alone for "add a regression test".

### Design: `codebase-design`, `architect`, `/improve-codebase-architecture`

`codebase-design` is the shared vocabulary (module, interface, depth, seam, adapter) and heuristics such as the deletion test. `architect` compares structurally different designs and records the chosen one. `/improve-codebase-architecture` finds where to apply them across a codebase.

### PR text: `file-pr` and `/pr`

`file-pr` drafts by default and files when you ask. `/pr` is its typed body-only entry; it files only if the same message asks for that or the task already authorizes filing.

### Finishing: `babysit-pr`, `/full-send`, `/full-stop`

`babysit-pr` watches an existing PR to ready and never merges. `/full-stop` takes a change from code to a ready PR. `/full-send` does the same and then merges through its gate.

### Verification: `result-verification`, `create-verification-skill`, `/maintain-verification-skill`

`result-verification` decides whether delivered work is accepted. When the real surface has no repeatable way to drive it, `create-verification-skill` writes a project driver named `verify-<project>-<surface>`. `/maintain-verification-skill` audits such a driver later.

### Records: `decision-log`, `/handoff`, `recall`, `/ketchup`, `domain-modeling`

`decision-log` is the authoritative run record: `PLAN.md`, `LOG.md` and `DECISIONS.md`. `/handoff` writes a temporary note that points at it. `recall` finds a run you cannot locate. `/ketchup` summarizes the current chat. `domain-modeling` keeps project-level ADRs, not run-level choices.

### Environment: `project-guardrails`, `correct`, `toolchain-upgrade`

`project-guardrails` inventories and wires checks across a project. `correct` turns one recurring mistake into one failing check, at the highest layer that can hold it. `toolchain-upgrade` makes a tooling bump's rule changes visible and decided.

### Planning: `work-decomposition` and `/to-tickets`

`/to-tickets` writes tickets from a spec, for people and agents. `work-decomposition` imports approved tickets exactly, or plans generic work, and decides owners, order and a finite budget for agents.

## What the evals say about choosing

Paired evals compare each skill with a run that lacks it. In several samples the plain model already did the job well, so the skill matched rather than beat it: in the PR #5 to #7 Codex samples, `research`, `how`, `diagnosing-bugs`, `grill-me`, `bro` and `pr` matched the no-skill baseline in most examples. Use them for consistency, explicit limits and authority boundaries, not for a different answer.

The clearest recorded gains were in authority and evidence: `/to-spec` producing stories with Proof and hashed sources, `/to-tickets` running its importer, `agent-briefing` embedding the communication contract and named Proof, `result-verification` refusing false-green work, `file-pr` keeping body-only drafts local, `fix-ci` binding the first causal error, and the thin typed entries stopping when their parent skill is missing instead of improvising.

These are single-sample observations on small fixtures, not population estimates. [How the collection is made](how-and-why.md#what-evaluated-means) explains what the status does and does not claim.
