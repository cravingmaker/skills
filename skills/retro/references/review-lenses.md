# Review lenses

Read this when selecting the useful dimensions of a retro or reconciling competing findings. These are lenses for one bounded investigation; they do not prescribe a panel or number of agents.

## Judgment

Find mistakes, corrections, user preferences, choices, and friction that change future decisions. State the general rule and the exact event that supports it. Separate a durable pattern from a one-off problem, a contradicted preference, or a fact likely to drift. Check the target guidance before proposing an edit: an existing clear rule may have been ignored rather than omitted.

## Tooling and access

Inspect navigation pointers, installed tools, project check commands, CI wiring, test entry points, and missing information. Ask whether the agent could have fetched context through an available connected tool instead of making the human supply it. Support that finding with the actual available capability and referenced context; an imagined tool is insufficient. A concrete discovery that survives code drift can earn a pointer; changing flags and versions belong with their actual source or help.

## Divergent and downstream effects

Look for a plausible explanation that contradicts the obvious lesson. Check skipped artifact proof, lucky test paths, downstream callers, implicit scope assumptions, and second-order costs. Identify what would discriminate between the competing explanations. An unsupported architecture concern remains a hypothesis rather than a proved session cause.

## Incident dimensions

| Dimension | Evidence to compare |
| --- | --- |
| Skill timeline | Actual reads or invocations, visible trigger descriptions, human requests, late or missed use, and other tools involved |
| Plan adherence | Accepted steps against executed actions, with resumes, compaction, scope changes, skips, and unexplained additions |
| Repeated work | Same tool and target or query, repeat count, changed inputs, corrections, or invalidated evidence that explains the repeat |
| Stumbles | Failure record, retry or revert, correction, permission or quota failure, and the subsequent recovery or unresolved state |
| Quality evidence | Claims of completion against relevant commands, results, artifact revisions, review feedback, and acceptance criteria |
| Request conflicts | Attributable human constraints against each other or loaded instructions, the resolution, and its authority |
| Cost and time | Verified counter semantics, compatible totals, timestamp intervals, large results, repeats, and associated sessions |

Choose dimensions relevant to the stated complaint and disclose what was not examined. A re-read after an edit or an invalidated check can be justified; repeat count alone is not waste. Supported earlier proof can remain valid across turns when its inputs and artifact are unchanged. Compare feedback with the actual fix or reasoned rejection; acknowledgment alone does not close it.

## Synthesis

Give each material finding a stable ID, consequence, evidence pointer, strongest competing explanation, and proposed destination. Require durability, specificity, and a change to a future decision. Use the existing capability first, and distinguish a body defect from a missed trigger or execution failure. Corroboration adds evidence only when it contributes a separate source or test; repeated opinions are not votes that prove a claim.

Apply the main skill's check-over-prose step before accepting an instruction edit. Classify accepted, rejected, and deferred items, retaining the reason and missing evidence. Read the destination guidance and merge or move existing meaning before adding text. New capabilities need a recurring, distinct job that lacks an existing home. No finding is a valid result; do not manufacture a lesson or file backlog items merely to fill a list.
